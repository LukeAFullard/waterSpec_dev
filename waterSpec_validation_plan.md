# waterSpec Validation Plan

**Package:** [`waterSpec`](https://github.com/LukeAFullard/waterSpec_dev) — spectral analysis of (environmental / hydrological) time series
**Purpose of this document:** an exhaustive, checkbox-driven test plan to confirm that `waterSpec`'s statistical outputs (spectral slopes β, Haar slopes/H, breakpoints, peaks, cross-correlations, hysteresis, intermittency corrections, uncertainty intervals) match theoretical expectations on data whose "ground truth" is known by construction, before trusting the package on real, noisy field data.

**How to use this document (for the executing agent):**
- Each test is a single checkbox `- [ ]`. Check it only once the **Pass criterion** is met and the artifact (script + output) exists on disk.
- Work top-to-bottom within a section; sections are ordered roughly by dependency (simulation infrastructure → basic spectral recovery → advanced features → real-data/regression checks).
- Every test should be a standalone, re-runnable script under `validation/` (create this folder if it doesn't exist) that: (1) generates synthetic data with a fixed seed, (2) runs the relevant `waterSpec` function/class, (3) asserts numerically against the pass criterion, (4) prints a PASS/FAIL line, (5) saves a diagnostic plot to `validation/plots/`.
- Use multiple random seeds (a "trial") per test unless stated otherwise, and report the **fraction of trials passing**, not just a single run — spectral slope estimation has genuine sampling variance, and single-seed failures are not necessarily bugs.
- Where a "tolerance" is given, treat it as a first estimate. If a well-implemented test fails consistently across seeds/N, that is a genuine finding — record it in `validation/FINDINGS.md` rather than loosening the tolerance to force a pass.
- Existing repo assets to reuse rather than duplicate: `src/waterSpec/utils_sim/tk95.py` (`simulate_tk95`, colored-noise generator), `src/waterSpec/utils_sim/models.py` (`power_law`, `red_noise_psd`), `tests/test_multifractal_slopes.py` and `tests/test_synthetic.py` (existing synthetic-data unit tests — read these first so this plan does not just re-implement what's already covered), `validation/demonstrate_intermittency.py` (log-normal cascade generator + K(2) recovery), `docs/validation/*.md` (existing validation narrative — this plan should produce new evidence to append there, not contradict it without investigation).

## 0. Setup & Infrastructure

- [x] **0.1** Clone/install the package in editable mode with test extras: `pip install -e '.[test]'`. Confirm `import waterSpec` succeeds and `waterSpec.__version__` resolves.
- [x] **0.2** Confirm optional dependencies used by the tests below are installed: `astropy` (Lomb-Scargle), `statsmodels` (LOESS detrending), `piecewise_regression` (segmented fits), `ruptures` (PELT changepoint), `mannks` (Haar segmentation). Run `pytest tests/ -q` once and confirm the existing test suite is green **before** adding new validation on top of it — if the existing suite is red, fix or document that first.
- [x] **0.3** Create `validation/` with subfolders `plots/`, `data/`, `results/` and a `common.py` module containing (Note: all results should be recorded in this `validation/` folder and ideally each section should have a markdown report in its own subfolder):
  - A colored-noise generator wrapping `simulate_tk95(psd_func=power_law, params=(beta, amp), N=N, dt=dt, seed=seed)` for a target β (recall `power_law(f, beta, amp) = amp * f**(-beta)`, i.e. PSD ∝ f^(-β), matching waterSpec's sign convention where P(f) ∝ f^(-β)).
  - A broken-power-law generator (either via a custom `psd_func` passed to `simulate_tk95`, or by concatenating/blending two `simulate_tk95` runs — validate whichever approach is chosen against the known β's before using it downstream, see Section 2).
  - An uneven-sampling function that takes an evenly-sampled series and returns a random/patterned subset (see Section 3 for the specific schemes required).
  - A seasonality-injector that adds a sinusoid (or sum of harmonics) of specified period(s), amplitude, and phase to a base series.
  - A results-recording helper that appends `{test_id, seed, params, estimate, truth, ci_low, ci_high, pass}` rows to a CSV in `validation/results/`, so a final summary table can be generated automatically (see Section 15).
- [x] **0.4** Decide and document the **global tolerance policy**: e.g. for N ≥ 2000-point single-slope recovery, require the true β to fall inside the reported bootstrap CI in ≥ 90% of 30 trials (i.e. close to nominal coverage for a ~95% CI, allowing Monte Carlo slack), AND the mean point estimate to be within ±0.15 of truth. Record this policy at the top of `validation/README.md` so every subsequent test references it instead of inventing ad hoc thresholds.
- [x] **0.5** Fix and document a global RNG seeding strategy (e.g. `seed = 1000*section + trial_index`) so every test is exactly reproducible and seeds never collide across sections.

## 1. Colored Noise Recovery — Lomb-Scargle (evenly sampled baseline)

Goal: confirm `calculate_periodogram` + `fit_standard_model` recover the correct β for classic colored-noise classes on *evenly sampled, gap-free* data — the easiest possible case and the foundation everything else builds on. Note: This section should also test the Haar method on the evenly sampled data to establish a baseline for Haar.

For each noise color below: generate with `simulate_tk95`, run `calculate_periodogram(time, data, ...)` then `fit_standard_model(frequency, power, method="theil-sen", ci_method="bootstrap")` (also repeat with `method="ols"`, and similarly for Haar), and compare the recovered β against the target. Use N = 4096 points, 30 seeds per case, dt = 1.

- [ ] **1.1 White noise** (β = 0, target: uncorrelated Gaussian). Pass: mean β̂ within ±0.15 of 0; 0 ∈ CI in ≥90% of trials.
- [ ] **1.2 Pink noise** (β = 1, 1/f noise). Pass as above centered on 1.
- [ ] **1.3 Brown/red noise (random walk)** (β = 2). Pass as above centered on 2. Note: at β=2 low-frequency bins have high variance/leverage — check whether excluding the lowest 1–2 frequency bins from the fit (if the package supports/needs a `min_freq`/frequency-range argument) improves stability, and document the finding either way.
- [ ] **1.4 Blue noise** (β = −1, anti-persistent). Pass as above centered on −1.
- [ ] **1.5 Violet/black noise** (β = −2). Pass as above centered on −2.
- [x] **1.6 Intermediate/fractional slopes**: β ∈ {0.3, 0.7, 1.3, 1.7} (spanning fGn/fBm boundary at β=1). Pass as above; specifically confirm the package does **not** show a systematic bias/discontinuity right at β=1 (the fGn↔fBm boundary), since this is a common failure mode in naive spectral estimators.
- [x] **1.7 Amplitude/units invariance**: repeat case 1.2 (pink noise) with the amplitude parameter scaled by 1×, 100×, 0.01× and with `dt` changed (1, 3600, 86400 — i.e. seconds/hours/days). Pass: recovered β is invariant to amplitude and to the numeric value of `dt` (only β, not amplitude or units, should matter) — confirms the fit is not accidentally sensitive to absolute scale.
- [x] **1.8 Sample-size sensitivity**: repeat pink noise (β=1) at N ∈ {128, 512, 2048, 8192, 32768}. Pass: bias trends toward zero and CI width shrinks monotonically as N grows; document the smallest N at which mean bias is under ±0.1 — this becomes a documented "minimum recommended sample size" for LS.
- [x] **1.9 `theil-sen` vs `ols` fit method comparison**: for each color in 1.1–1.5, compare the two fitting methods' bias and CI width on the same simulated realizations. Pass: both recover the correct β within tolerance; document which is more robust in the presence of outlier frequency bins (this sets expectations rather than a strict pass/fail).
- [x] **1.10 `parametric` vs `bootstrap` CI comparison**: for pink noise (β=1), compare CI width and empirical coverage (over ≥100 trials) for `ci_method="parametric"` vs `ci_method="bootstrap"` with `bootstrap_type` ∈ {"block","wild","pairs","residuals"}. Pass: report empirical coverage of the nominal 95% CI for each combination in a table; flag any combination whose empirical coverage is below ~85% (under-coverage) as a finding.

## 2. Segmented / Broken Power-Law Spectra (Spectral Slope Splits)

Goal: confirm `fit_segmented_spectrum` (LS side) and Haar's `max_breakpoints`/segmented fit correctly recover a known breakpoint frequency/lag and the two slopes on either side, and that automatic model selection (`ModelSelector` / BIC-AIC logic in `run_full_analysis`) correctly chooses the segmented model when a real break exists and the single-slope model when it doesn't.

- [x] **2.1 Single clean break, LS**: construct a synthetic PSD with β₁ = 0.3 for f < f_break and β₂ = 1.8 for f > f_break (or vice-versa), at a break placed well inside the resolvable frequency range (e.g. at the geometric-mean frequency). Run `fit_segmented_spectrum`. Pass: recovered β₁, β₂ within ±0.2 of truth; recovered break frequency within ±30% (log scale) of truth, across ≥20 seeds.
- [x] **2.2 Break location sweep**: repeat 2.1 with the break placed at 10%, 25%, 50%, 75%, 90% of the log-frequency range. Pass: document how estimation error in β₁/β₂/break-location grows as the break approaches either edge (expect degradation near edges due to too few points in one segment) — this defines a "safe" break-location range to disclose in the package docs.
- [x] **2.3 Slope-difference sensitivity**: fix break at 50%, vary |β₂ − β₁| ∈ {0.2, 0.5, 1.0, 2.0}. Pass: confirm model-selection (Section 2.5) only reliably prefers the segmented model once the slope difference exceeds some threshold — document that threshold (expect small differences, e.g. 0.2, to be hard to detect against a single-slope null with realistic noise).
- [x] **2.4 No break (negative control)**: generate pure single-slope pink noise (no break at all) and run `fit_segmented_spectrum` alongside `fit_standard_model`. Pass: BIC/AIC-based selection (or `ModelSelector.select_best_model`) prefers the single-slope model in ≥90% of ≥20 trials — i.e. confirm the package does not overfit spurious breakpoints on smooth power-law data.
- [x] **2.5 Automatic model selection end-to-end**: run `Analysis.run_full_analysis(..., max_breakpoints=1)` (full pipeline, not the low-level fit functions) on both a true-break dataset (2.1) and a no-break dataset (2.4), each for ≥20 seeds. Pass: correct model chosen in ≥90% of trials for each case; record the confusion matrix (break present/absent × segmented/single selected).
- [x] **2.6 Two breakpoints**: construct a three-segment PSD (β₁, β₂, β₃ with two breaks) and confirm `max_breakpoints=2` recovers all three slopes and both breakpoints within tolerance. If two-breakpoint recovery is unreliable at realistic N, document minimum N required.
- [x] **2.7 Haar-side segmented fit**: repeat 2.1–2.4 using `fit_haar_slope`/`fit_segmented_haar` (via `HaarAnalysis.run(max_breakpoints=1)`) instead of LS, using the Haar-slope-to-β mapping β = 2m + 1. Pass criteria mirror 2.1/2.4. This directly exercises the `MannKS`-based segmented regression mentioned in the README.
- [x] **2.8 Changepoint-in-time vs changepoint-in-frequency (do not conflate)**: confirm `detect_changepoint_pelt` (which detects a *temporal* regime shift — a changepoint in the value of the series over time, used by `Analysis._detect_changepoint` / `run_analysis` before/after split) is validated **separately** from the *spectral* breakpoint tests above. Build a series with a genuine step-change or trend-change at a known time index (e.g. mean shift, or variance shift, or a change from red to white noise partway through) and confirm `detect_changepoint_pelt` recovers the correct time index within a small tolerance (e.g. ±2% of series length), across `model` ∈ {"rbf","l2","l1","normal","ar"}. Document which `model` choice is most accurate for each of: mean-shift, variance-shift, and slope/persistence-shift scenarios — this is exactly the "split time series before/after an event" workflow the package advertises.
- [x] **2.9 Before/after split significance testing**: using the series from 2.8 (variance/persistence-shift case), run the package's before/after-changepoint analysis path (`Analysis.run_full_analysis` with the built-in changepoint detection, or manual `_prepare_changepoint_segments`) and confirm it reports a statistically significant difference in β between the two halves when a real difference exists (Section 2.3's larger slope-differences), and reports no significant difference on a negative control with the same β before and after. This is the core "quantify changes in spectral slopes across interventions" feature from the README — validate it end-to-end, not just its pieces.

## 3. Sampling Schemes (Even vs Uneven)

Goal: confirm both LS and Haar degrade gracefully, and Haar remains more reliable than LS, as sampling becomes irregular — the central claim of the package's method-selection guidance ("Haar recommended for unevenly sampled data").

For each scheme, use pink noise (β=1, easy reference case) AND one fBm-like case (β=1.6) AND one anti-persistent case (β=0.3) as three sub-cases, ≥20 seeds each, comparing LS vs Haar recovered β against truth.

- [x] **3.1 Fully even sampling (baseline / already covered by Section 1)** — just cross-reference, no new test needed here.
- [x] **3.2 Uniform-random missingness**: drop a uniform-random fraction of points at {10%, 30%, 50%, 70%, 90%} missing. Pass: for each missing fraction, both methods' bias/CI-width are recorded; confirm the expected qualitative result that Haar's bias grows more slowly than LS's as missingness increases (specifically check whether LS shows the "bias toward higher/lower β under heavy gaps" pattern already flagged in the README caution and in `tests/test_multifractal_slopes.py::test_uneven_sampling`/`test_haar_ls_uneven_comparison` — extend those fractions rather than duplicate them).
- [x] **3.3 Clustered/bursty missingness**: remove entire contiguous blocks (e.g. simulate "sensor offline for N% of the record" as a few long gaps rather than many short ones) at the same total missing fractions as 3.2. Pass: compare against 3.2's uniform-random-gap results — clustered gaps are known to be harder for spectral recovery in general, so this specifically tests whether waterSpec's Haar implementation (with `overlap=True`/`min_samples_per_window`) tolerates block gaps as well as scattered ones.
- [x] **3.4 Realistic irregular field-sampling pattern**: mimic a typical water-quality grab-sample regime — e.g. sampling interval drawn from a distribution with occasional long tails (e.g. weekly nominal spacing with random jitter ±2 days, occasional 2–3 month gaps in winter/high-flow season, occasional dense storm-chasing bursts of sub-daily samples). Pass: qualitative — confirm Haar recovers β within the same tolerance as 3.2's matched missing-fraction case; if it does notably worse, that's a genuine finding about clustering/seasonality-correlated gaps, not a bug to hide.
- [x] **3.5 Duty-cycle/periodic sampling**: sample only e.g. business days, or only daytime hours, to create a strictly periodic (not random) irregular pattern. Pass: confirm this doesn't introduce a spurious peak at the duty-cycle frequency in LS peak detection (cross-reference Section 6) and doesn't bias the Haar slope; this is a classic aliasing trap for irregular-sampling methods.
- [x] **3.6 Minimum-data-density stress test**: push missingness to the point of failure (e.g. 95%, 99%) purely to characterize *where* the package starts issuing warnings or degrading ungracefully (silently wrong output vs. explicit warning vs. clean exception). Pass: confirm the package emits an appropriate warning (e.g. the existing `CV_THRESHOLD_FOR_IRREGULAR_SAMPLING` warning in `frequency_generator.py`, or equivalent Haar warnings about `min_samples_per_window`) rather than silently returning a misleading, unflagged number.
- [ ] **3.7 Haar `overlap` on/off comparison under uneven sampling**: repeat 3.2 (uniform missingness) at 50% missing with `overlap=True` vs `overlap=False` in `HaarAnalysis.run`. Pass: `overlap=True` shows tighter CIs / less bias for the same data (per README's claim that overlapping windows "maximize data usage"); quantify the improvement.
- [ ] **3.8 Small-sample bias correction (`aggregation="std_corrected"`)**: at small window sample counts (e.g. deliberately using `min_samples_per_window` near its floor, or very short series), compare `aggregation="mean"` vs `aggregation="std_corrected"` recovered β against truth. Pass: confirm `std_corrected` reduces small-sample bias relative to `mean`, consistent with the README's claim that it "matches GapWaveSpectra." Cross-reference against `validation/compare_gapwavespectra.py`, which already exists for this — extend rather than duplicate, and note any discrepancy from its published conclusions.
- [ ] **3.9 Duplicate timestamps / non-monotonic input**: feed data with (a) exact duplicate timestamps, (b) out-of-order timestamps, (c) both. Pass: confirm `data_loader.py`'s `_check_monotonicity_and_duplicates`/`_convert_and_sort_time` either cleanly sorts/deduplicates with a warning, or raises a clear, documented exception — never silently produces a wrong spectrum from unsorted input.

## 4. Seasonality / Periodicity

Goal: confirm the package both **detects known periodicities as significant peaks** (LS side) and **correctly separates/corrects for periodicity when estimating the underlying colored-noise slope** (Haar `correct_periodicity` side), and does not falsely invent cycles that aren't there.

- [x] **4.1 Pure periodic + white noise, peak detection**: sinusoid of known period (e.g. 365.25 days, or 24 h for sub-daily data) with amplitude several × the noise SD, added to white noise, evenly sampled. Run `find_significant_peaks`/`Analysis`'s peak-detection step with `peak_detection_method="fap"`. Pass: the true period is recovered (frequency within ±(1/T) resolution) and flagged significant at the chosen `fap_threshold`, across ≥20 seeds.
- [x] **4.2 Peak detection with `residual`/FDR method**: repeat 4.1 with `peak_detection_method="residual"`. Pass: same detection criterion; compare false-positive/false-negative rates between `"fap"` and `"residual"` methods (cross-reference `validation/validate_peak_detection.py` and `validation/validate_peak_detection_sweep.py`, which appear to already do sweeps of this — read them first and extend coverage rather than re-deriving from scratch, e.g. add uneven-sampling to their sweep if not already present).
- [x] **4.3 Weak periodicity / detection threshold sweep**: sweep the sinusoid amplitude from far-above to far-below the noise floor (e.g. amplitude/noise-SD ∈ {5, 2, 1, 0.5, 0.2, 0.1}) and record the empirical detection rate at each amplitude, for both peak-detection methods. Pass: produces a monotonic detection-rate curve (a de-facto "power curve") with no reversals; a reversal (higher amplitude detected *less* often) would indicate a bug.
- [x] **4.4 Multiple simultaneous periodicities**: two or more known periods (e.g. annual + weekly, or annual + semi-annual harmonic) plus colored-noise background. Pass: both periods detected as separate significant peaks, and neither is misattributed to the other's harmonic.
- [x] **4.5 False-positive rate (negative control)**: run peak detection on pure colored noise (no injected periodicity) at several β values, ≥50 seeds each. Pass: empirical false-positive rate at `fap_threshold=0.01` is close to 1% (within Monte Carlo error, e.g. binomial CI); repeat for `peak_fdr_level=0.05` and confirm ~5%. This is the single most important peak-detection validation — a well-calibrated significance test is the entire point of using FAP/FDR rather than eyeballing the periodogram.
- [x] **4.6 Seasonality's effect on the *slope* estimate (contamination check)**: take a colored-noise series of known β (no periodicity) and add a strong seasonal cycle on top. Run standard `fit_standard_model`/`HaarAnalysis.run` **without** any periodicity handling. Pass: quantify how much the recovered β is biased by the presence of the un-corrected seasonal peak (expect measurable bias, especially if the seasonal period falls inside the fitted frequency/lag range) — this documents *why* correction matters, and gives a baseline to compare against 4.7.
- [x] **4.7 Haar periodicity correction (`correct_periodicity=True`)**: repeat 4.6 but run `HaarAnalysis.run(correct_periodicity=True, periodic_periods=[...])` (exercising `haar_periodicity.py`'s `correct_structure_function_for_periodicity`/`reconstruct_periodic_signal`/`compute_periodic_structure_function`). Pass: recovered β is substantially closer to the true underlying (non-seasonal) β than the uncorrected case in 4.6, across ≥20 seeds; quantify the bias reduction.
- [x] **4.8 Automatic period-candidate detection (`list_period_candidates`/`consolidate_periods`)**: if the package supports auto-detecting candidate periods (rather than requiring the user to supply `periodic_periods`), test that it correctly identifies the injected period(s) from 4.4/4.6 without manual specification, and that `consolidate_periods` correctly merges near-duplicate harmonic detections into one.
- [x] **4.9 Seasonality + uneven sampling combined**: repeat 4.7 (periodicity correction) under the moderate uneven-sampling scheme from 3.4 (realistic irregular field sampling). Pass: confirm correction still meaningfully improves β recovery when sampling is irregular, not just in the ideal evenly-sampled case — this is the realistic use case for the package's target domain (water quality grab samples), so it deserves its own explicit test rather than being assumed to follow from 4.7 and Section 3 independently.
- [x] **4.10 Non-sinusoidal periodicity (sawtooth/square-ish seasonal cycle)**: repeat 4.7 with a non-sinusoidal but still periodic seasonal shape (e.g. a skewed annual hydrograph shape) to confirm the correction isn't overfit to pure sinusoids and still helps (even if less perfectly) with harmonically-rich real-world seasonal shapes.

## 5. Multifractal / Intermittent Processes

Goal: validate the multifractal intermittency correction (K(2), β = 1 + 2H − K(2)) end to end — this is one of the more novel/complex claims in the README and deserves the most rigorous ground-truth testing.

- [x] **5.1 Reuse and extend the existing cascade generator**: start from `validation/demonstrate_intermittency.py`'s `generate_lognormal_cascade` (log-normal multiplicative cascade) and `fractional_integration`. Move/refactor this into `validation/common.py` as a reusable, seeded function `generate_multifractal_series(N, H_target, sigma_cascade, lambda_scale=2, seed=...)` returning `(time, data, true_H, true_K2, true_beta_multi)` computed analytically from the cascade parameters (per the derivation already in that script: K(2) = σ²·log(λ)·(2²−2)/... — confirm/derive the exact closed form being relied on and document it explicitly in the test file, don't just copy the commented derivation uncritically).
- [x] **5.2 Monofractal negative control (K(2) ≈ 0)**: run the full pipeline (`HaarAnalysis.run(calc_intermittency=True)` or `Analysis`'s `calc_intermittency=True`) on a plain fGn/fBm series (Section 1's TK95 series, not a cascade). Pass: estimated K(2) is not significantly different from 0 (within bootstrap CI) in ≥90% of ≥20 trials, and β_standard ≈ β_multi (they should coincide for a monofractal process) — confirms the correction doesn't invent intermittency where none exists.
- [x] **5.3 Known-intermittency positive control**: run the same pipeline on the cascade-based series from 5.1 at several `sigma_cascade` values (e.g. 0.2, 0.4, 0.6 — increasing intermittency strength). Pass: recovered K(2) increases monotonically with `sigma_cascade` and is within a documented tolerance (start with ±30% relative, tighten once a first pass establishes achievable precision) of the analytically-known true K(2), across ≥20 trials per level; recovered H (zeta(1)) matches the target H used in `fractional_integration`.
- [x] **5.4 β_multi vs β_standard divergence**: for the same 5.3 cascades, confirm β_multi = 1 + 2H − K(2) differs from the naive/standard single-moment β by an amount consistent with the known K(2) — i.e. reproduce the "dual reporting" the README describes, and confirm it is *quantitatively* correct, not just qualitatively different.
- [x] **5.5 Sensitivity to intermittency of the *standard* (non-corrected) LS/Haar slope**: quantify, across the `sigma_cascade` sweep in 5.3, how much the *uncorrected* β estimate is biased by ignoring intermittency — directly validates the README's warning that standard β "ignores extreme events" and gives users a concrete sense of the magnitude of that bias in this package's implementation.
- [x] **5.6 Real-world-like intermittent signal (storm-flashy hydrology proxy)**: construct a more realistic intermittent series by superimposing occasional large multiplicative "storm" bursts on an otherwise smooth persistent background (rather than a pure cascade) — e.g. baseflow fBm plus randomly-timed exponential-decay storm pulses of random magnitude. Pass: qualitative — confirm `calc_intermittency=True` produces a materially different (and more physically sensible, e.g. more consistent across repeated storm realizations) β_multi than β_standard, and that the correction doesn't blow up or become numerically unstable when bursts are rare/extreme.
- [x] **5.7 Interaction with segmentation (Section 2)**: confirm `calc_intermittency` and `max_breakpoints`/segmented Haar fits can be used together without conflict (e.g. run on the broken-power-law + intermittency combined case) and that results remain sensible (this exercises a code path combination that may not be tested elsewhere).
- [x] **5.8 Interaction with uneven sampling (Section 3)**: repeat 5.3 (positive-control cascade) under moderate uneven sampling (30% random missingness from 3.2). Pass: confirm K(2)/H recovery degrades gracefully (wider CIs) rather than catastrophically or silently biased — intermittency correction combined with gappy data is exactly the real-world combination the package is meant to handle.

## 6. Bootstrap Confidence Intervals & Uncertainty Quantification (cross-cutting)

Goal: rather than checking CI coverage piecemeal inside each section above, run one dedicated, larger-scale calibration study, since correct uncertainty quantification is arguably the single most safety-critical property of the package (users will make decisions based on whether a CI excludes some benchmark value).

- [x] **6.1 Coverage calibration table**: for β ∈ {0, 0.5, 1, 1.5, 2}, N ∈ {512, 2048, 8192}, sampling ∈ {even, 30% uneven}, method ∈ {LS theil-sen, LS ols, Haar mean, Haar std_corrected}, `bootstrap_type` ∈ {block, wild, pairs, residuals}: run ≥100 trials each (this is a large grid — parallelize, or reduce to the most policy-relevant subset if compute-constrained, but document the reduction) and record empirical coverage of the nominal 95% CI. Pass: flag (not silently drop) any cell with coverage < 85% or > 99% as needing investigation; produce a single summary table/heatmap as the deliverable.
- [x] **6.2 CI width scaling with N**: confirm CI width shrinks roughly as expected (e.g. ~1/√N-ish, though spectral slope CIs won't follow this exactly — just confirm monotonic shrinkage with more data, no pathological widening).
- [x] **6.3 Parametric vs bootstrap CI agreement**: where both are available (LS `fit_standard_model`), confirm parametric and bootstrap CIs roughly agree on well-behaved (evenly-sampled, Gaussian, monofractal) data, and diverge sensibly (bootstrap should be more honest/wider) once heteroscedasticity, autocorrelated residuals, or non-Gaussianity are introduced — construct at least one deliberately heteroscedastic case (e.g. multiplicative noise) to test the `bootstrap_type="wild"` recommendation specifically.
- [x] **6.4 Seed reproducibility**: confirm that calling any bootstrap-CI function twice with the same `seed` gives bit-identical results, and with `seed=None` gives different results — a basic but essential regression check (cross-reference `tests/test_rng_and_bootstrap.py`/`tests/test_utils_rng.py`, extend if these don't already cover every entry point that accepts a `seed`).

## 7. Preprocessing Pipeline

- [x] **7.1 Detrending (linear)**: add a known linear trend to a colored-noise series; confirm `detrend`/`preprocess_data` removes it (residual trend ≈ 0) and that the resulting spectral slope estimate matches the untrended-data baseline (i.e. confirm detrending prevents the trend from contaminating β as low-frequency excess power).
- [x] **7.2 Detrending (LOESS, `detrend_loess`)**: repeat 7.1 with a nonlinear (e.g. quadratic or slowly-varying) trend that a linear detrend would leave residual bias in; confirm LOESS detrending removes it and recovers the correct β better than linear detrending on this nonlinear-trend case specifically (a comparative test, not just each in isolation).
- [x] **7.3 No detrending baseline (negative control)**: confirm that with no trend injected, detrending doesn't distort a known-β series either (i.e. detrending isn't harmful when unnecessary) — check both linear and LOESS.
- [x] **7.4 Log transform**: for a multiplicative/lognormal-noise series (values must stay positive — e.g. exponentiate a Gaussian colored-noise series), confirm `log_transform` + subsequent spectral fit recovers the correct β of the *underlying additive* process, vs. fitting the raw (untransformed) series which should give a distorted/incorrect result. This directly matters for water-quality concentration data, which is typically lognormal.
- [x] **7.5 Normalization**: confirm `normalize` doesn't change the recovered β (only rescales values) — a units-invariance check analogous to 1.7, run through the actual `preprocess_data` pipeline this time rather than the raw fitting functions.
- [x] **7.6 Censored data handling — `strategy="drop"`**: build a series with a known fraction of values artificially replaced by left-censored strings (e.g. `"<0.01"`) at a known detection limit; confirm `handle_censored_data(strategy="drop")` converts them to NaN and that downstream fitting either ignores or explicitly errors on remaining NaNs (confirm which, and that it's documented behavior, not silent corruption).

## 8. Bivariate / Multivariate Cross-Haar Analysis

Goal: validate `BivariateAnalysis` and `multivariate.calculate_partial_cross_haar` on synthetic pairs with **known** true correlation/lag/spuriousness structure — this is hard to validate on real data because the truth is unknown, so synthetic ground truth is essential here.

- [x] **8.1 Perfectly correlated pair (positive control)**: two identical (or near-identical, differing by small independent noise) colored-noise series. Run `run_cross_haar_analysis`. Pass: cross-correlation ≈ 1 (or close to it, discounted by the added noise fraction) at all lags, with tight/appropriate CIs.
- [x] **8.2 Independent pair (negative control)**: two independently-generated colored-noise series of the same β. Pass: cross-correlation ≈ 0 within CI at most/all lags, across ≥20 seeds (also gives an empirical false-positive rate for `calculate_significance`, analogous to 4.5).
- [x] **8.3 Known lead-lag relationship**: generate series B as a time-shifted (by a known lag τ₀) and optionally rescaled copy of series A plus independent noise. Run `run_lagged_cross_haar` and `calculate_ls_cross_spectrum`/`calculate_time_lag`. Pass: recovered lag matches τ₀ within tolerance (e.g. within one sampling interval or a small fraction of τ₀), across ≥20 seeds and at least 2–3 different τ₀ magnitudes (short, medium, long relative to the record length).
- [x] **8.4 Spurious correlation via common driver — partial cross-Haar**: construct C and Q as two independent linear (or nonlinear) functions of a shared driver R (e.g. "Rain") plus independent noise each, such that C and Q are correlated with each other *only* through R, with no direct C↔Q relationship. Run `calculate_partial_cross_haar(time, C, Q, R, ...)`. Pass: raw cross-Haar correlation ρ(C,Q) is significantly non-zero, but partial correlation ρ(C,Q|R) collapses toward zero — validating the core "distinguish direct vs spurious correlations" README claim.
- [x] **8.5 Genuine direct correlation surviving partialling**: construct C and Q with both a genuine direct relationship AND a shared confound R. Pass: ρ(C,Q|R) remains significantly non-zero (smaller than raw ρ(C,Q) but not collapsed to zero) — confirms partialling doesn't over-correct and destroy real signal.
- [x] **8.6 `align_data` correctness**: build two series on deliberately mismatched/irregular timestamps with a known true relationship, and confirm `align_data(tolerance=..., method='nearest')` produces the expected aligned pairs (check a handful by hand) and that mismatches beyond `tolerance` are correctly excluded rather than wrongly paired.
- [x] **8.7 Percentile/extreme-focused cross-Haar**: repeat 8.1/8.2 with `statistic1="percentile", percentile1=95` (etc., per the README's extremes example) to confirm the percentile-based cross-correlation machinery gives sensible results (high correlation for the positive control, near-zero for the negative control) and not just the default mean-based statistic.
- [x] **8.8 Hysteresis metrics ground truth**: construct C-Q pairs with **known, designed hysteresis loop direction and shape** — e.g. clockwise loop (C leads Q, common for "flushing" behavior) vs counter-clockwise loop (Q leads C, "dilution"/mobilization behavior), built by explicit time-lagging one series relative to the other with a known functional C(Q) relationship at a chosen tau. Run `calculate_hysteresis_metrics(tau=...)`. Pass: recovered loop `direction` matches the constructed direction in ≥90% of trials, and loop `area` scales sensibly with the constructed lag magnitude/nonlinearity strength (larger designed lag/loop → larger recovered area).
- [x] **8.9 Zero-hysteresis negative control**: C and Q with no lag and a simple monotonic (linear) relationship — no looping at all. Pass: recovered `area` ≈ 0 within tolerance.
- [x] **8.10 Spectral coherence (`calculate_spectral_coherence`)**: for the 8.1 (correlated) and 8.2 (independent) pairs, confirm coherence is high across relevant frequencies for 8.1 and near the theoretical null level for 8.2.
- [x] **8.11 `calculate_multivariate_fluctuations`**: if this exposes anything not already covered by the bivariate tests above (e.g. >2 variables, or a different aggregation), add a targeted test; otherwise note here that it's covered indirectly and move on rather than padding the plan.

## 11. Surrogate-Based Significance Testing

Goal: confirm the four surrogate generators (`generate_phase_randomized_surrogates`, `generate_block_shuffled_surrogates`, `generate_power_law_surrogates`, `generate_iaaft_surrogates`) each (a) preserve the properties they're supposed to preserve and destroy the ones they're supposed to destroy, and (b) yield correctly-calibrated p-values via `calculate_significance_p_value` when used as a null distribution.

- [ ] **11.1 Phase-randomized surrogates preserve the power spectrum**: generate surrogates of a known-β colored-noise series; confirm each surrogate's own recovered β (via the standard LS/Haar pipeline) matches the original's β distributionally (should be near-identical since phase randomization preserves the power spectrum by construction), while any *nonlinear* structure (if injected into the original, e.g. via a nonlinear transform) is destroyed. This double-checks the surrogate method is doing what phase-randomization is supposed to do, not just "some kind of shuffle."
- [ ] **11.2 Block-shuffled surrogates preserve short-range structure, destroy long-range**: confirm block-shuffled surrogates of an fBm-like series retain short-lag autocorrelation similar to the original (within a block length) but show reduced/destroyed long-lag structure — check this holds across a couple of block-size settings if the function exposes that parameter.
- [ ] **11.3 IAAFT surrogates preserve both amplitude distribution and (approximately) the power spectrum**: confirm surrogates from `generate_iaaft_surrogates` match the original series' marginal value distribution (e.g. same histogram/quantiles) *and* approximately the same power spectrum — the two properties IAAFT is specifically designed to jointly preserve, unlike simple phase randomization (which preserves the spectrum but Gaussianizes the marginal).
- [ ] **11.4 Power-law surrogates match target β exactly by construction**: sanity-check `generate_power_law_surrogates` directly against a target β (this should be closely related to/reuse the TK95 approach in Section 1 — confirm consistency rather than finding two different code paths give different answers for "generate me β=1 noise").
- [ ] **11.5 Surrogate-based significance calibration (the key test)**: use each surrogate type as the null distribution via `calculate_significance_p_value` in a scenario with **no real effect** (e.g. testing whether a cross-Haar correlation between two independent series, per 8.2, is "significant" against a surrogate null) across ≥100 trials. Pass: empirical false-positive rate at p<0.05 is close to 5%, analogous to 4.5. This is the single most important surrogate-testing validation — a mis-calibrated surrogate null is worse than no significance test at all, since it creates false confidence.
- [ ] **11.6 Surrogate-based significance power test (positive control)**: repeat 11.5 with a real, known effect present (e.g. the genuine lead-lag pair from 8.3, or the direct-correlation-surviving-partialling case from 8.5) and confirm the surrogate-based test correctly rejects the null at a reasonable rate (statistical power) — report power vs. effect-size, not just a binary pass/fail, since power inherently depends on effect size and N.
